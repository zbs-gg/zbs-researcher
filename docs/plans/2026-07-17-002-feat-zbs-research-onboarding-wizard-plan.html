Goal Capsule

Objective. A PostHog-class onboarding wizard for the ZBS Research skill that takes a client from install to their first deep, multi-source, reaction-weighted research report with the minimum possible connections — ideally zero — and a clear, progressive path to unlock more depth, plus built-in demand signals that measure willingness to pay before anything paid is built.

Product authority. Nikita (owner). The wizard runs inside the Claude Code agent (the conversation is the wizard), so no separate binary. Free skill under the ZBS brand is the funnel; the paid hypothesis (managed Telegram + done-for-you for CIS niches) is validated by the demand signals, not assumed.

Decision this run: ship the full wizard with all tiers (Tier 0 → direct keys → OpenRouter → Telegram → TikTok/IG), not a narrow slice — Nik's explicit choice.

Open blockers: Arctic-Shift score-field availability (load-bearing for Reddit reaction-weighting); OpenRouter↔Perplexity access (smoke-test); where the demand signal lands (see Outstanding Questions).

Product Contract

Primary actor & context

  • Primary: Nik's client — a lite-technical operator on a Claude-Code-compatible agent host, who wants deep research without wiring a zoo of services.
  • Secondary: Nik himself (the self profile — power user, local $0 on his Mac); and the Claude Code agent, which executes the wizard as dialogue.

Core outcome

In minutes, with zero required keys, the client sees a real reaction-weighted research report; then chooses, one visible decision at a time, how much more depth to unlock — and can signal "I want the paid version" or "just host it for me" at any point without any silent account creation.

Product Requirements

A · The wizard (conversation-as-wizard)

IDRequirement
R1The wizard is the conversation — driven by AskUserQuestion modal steps on capable hosts, with a prose fallback on Codex/Cursor/Gemini-CLI. No separate installer binary.
R2On first run a SessionStart hook detects existing state (which keys/accounts are present) using a fixed lookup order — process env → project config → global config → OS keychain — so the wizard only asks for what it genuinely can't find.
R3Proof before ask: the wizard runs the $0 Tier-0 path and shows a real result before prompting for any paid key. Proof, not promise.
R4The welcome pitch is embedded inside the first wizard question, never sent as a standalone message (Claude Code folds standalone tool output behind "ctrl+o" and it goes unread — last30days #750).
R5Each setup path ends with a verification step that proves it works (a real report/segment produced), analogous to PostHog's first-dashboard / Sentry's test-event moment. A --diagnose/doctor self-report shows current state with no network call.

B · Progressive tiers (each gated behind one visible decision; show what's already unlocked free before pitching the next)

IDRequirement
R6Tier 0 — zero keys, works now: Hacker News, Reddit (Arctic-Shift), YouTube, GitHub, Polymarket, Meta Ad Library. This is the default floor; a client with no keys still gets a real report.
R7Tier 1 — own direct keys: paste a Gemini / Grok key for depth via each provider's native grounded lens (googleSearch, x_search). Independent blast-radius for clients who value reliability.
R8Tier 2 — one OpenRouter key routes all lenses through a single key. MUST use explicit provider-native tools (not the :online shortcut, which forces search every call), via raw HTTP (wrapper libs have Gemini-grounding bugs). Perplexity access smoke-tested before relied on.
R9Telegram (the moat): the wizard guides installing Telethon and parses on the client's behalf. It MUST show a hard warning to use a separate / secondary account, never the personal one (ban risk + personal-DM exposure). Explicit opt-in only.
R10TikTok / Instagram — optional, via a pay-per-use adapter (Apify or ScrapeCreators), for clients who don't want to fiddle with free-but-flaky OSS scrapers. Off by default.
R11GitHub issues + comments is a first-class scored source (product/competitor intelligence), not just repo search.
R12LinkedIn is de-prioritized — not in the default set (little original content; mostly reposts). May return later behind a flag.

C · Demand signals & monetization hooks

IDRequirement
R13An explicit "I want the paid version" action — never a silent auto-mint of third-party accounts (last30days #524 rejected exactly this; explicit opt-in is the intended model).
R14An explicit "just host it for me" (managed / done-for-you) action — a separate, clearly-named signal, not a hidden default.
R15Both signals are recorded so Nik can measure willingness to pay (who pressed what). The v1 job is measurement, not fulfillment — see Non-goals.

D · Deployment profiles & budget invariant

IDRequirement
R16Two deployment profiles, chosen by config: self (local, $0, Mac — MLX Whisper / local vision) and client/portable (cloud-cheap — Groq Whisper $0.04/hr, Gemini Flash vision sub-cent). Media transcription/vision backend is pluggable, not hardcoded local compute.
R17Budget invariant: no Anthropic/OpenAI API spend by default. Synthesis happens in the client's own Claude session; the OpenAI channel stays opt-in.

E · Differentiation baked in (the "why switch from last30days" list, from its own issue tracker)

IDRequirement
R18Runs on Windows out of the box. last30days has ~30 Windows-broken issues (SIGALRM/os.killpg/UnicodeEncodeError). ZBS uses stdlib + threading; Windows must be a verified-green target, stated loudly.
R19Clean security posture. last30days installs flag 🔴 High Risk (#565) — a hard stop for clients. ZBS ships least-privilege + a transparent "what it does / what it sends where," aiming for a clean scan. Plan-first transparency is the trust story.
R20Install that doesn't fail — passes claude plugin validate, correct skills/<name>/SKILL.md layout (last30days #237/#362 fail the validator).
R21Smarter ranking than vote-count-only (last30days #641 surfaces off-topic on niche topics): comment-evidence weighting + relevance floor + anti-bot signature (ideation idea #4) — matters most on Nik's niche topics.

Scope boundaries

In scope (v1)
  • Full conversational wizard (R1–R5)
  • All tiers 0→1→OpenRouter→Telegram→TikTok/IG (R6–R12)
  • Demand-signal buttons + recording (R13–R15)
  • Two deployment profiles (R16–R17)
  • Differentiation fixes vs last30days (R18–R21)
Out of scope / Non-goals (v1)
  • Actual managed hosting backend — only the signal button, not the hosting
  • Real payment/billing flow
  • Non-coder GUI/dashboard wrapper — stays a developer-installable skill (the 2nd competitive gap; a later bet)
  • LinkedIn connector
  • Fulfilling done-for-you delivery in-product (that's Nik's consulting, off-tool)

Success criteria / acceptance signals

  • A client goes from install → first real $0 report without entering any key.
  • Each tier unlocks behind one explicit decision; a zero-risk user can stop at Tier 0 and still get real value.
  • Windows run green; claude plugin validate passes; security scan is not High-Risk.
  • Demand signals are captured — Nik can see who pressed "want paid" / "host it for me".
  • Telegram onboarding never proceeds without the separate-account warning acknowledged.

Outstanding questions (for ce-plan / implementation)

  • Where does the demand signal land — a local log, a message to Nik's Telegram, a file, a lightweight endpoint? (Product: it's recorded; the destination is a plan decision.)
  • Telegram handoff mechanics — how the client supplies a session safely (the separate-account flow).
  • Gemini structured-JSON-output vs search-grounding are mutually exclusive through OpenRouter — reconcile with our output format.
  • "Just host it for me" — exact v1 behavior after the press (likely: notify Nik + confirmation to user; no real hosting yet).

Assumptions (verify in planning)

  • Arctic-Shift returns Reddit score fields (load-bearing for reaction-weighting; unconfirmed).
  • OpenRouter still exposes Perplexity Sonar (it has flip-flopped; smoke-test).
  • Clients are predominantly on Claude Code / compatible agent hosts (modal + prose fallback covers the rest).
  • YouTube-video multimodal grounding (Gemini ingesting a URL) is separate from googleSearch grounding — verify if depended on.
